# AGENTS.md

## Цель

Развернуть HTTP API для прогноза месячных продаж по парам `(shop_id, item_id)` с обученной моделью LightGBM. API должен быть доступен с машины, где он запущен, и по возможности с другой машины в локальной сети.

## Документация

- Диаграммы проекта лежат в `docs/uml/`. Развёртывание описано в `deployment.puml`, сценарий прогноза — в `sequence_predict.puml`.
- Справочный офлайн-расчёт — в `tmp/notebooks/3_models/lgbm/` и `tmp/scripts/`. Рабочий сервис запускается без `tmp/` и Jupyter.
- Если выбор реализации зависит от будущих изменений, уточни их у пользователя.
- Необходимость изменения документации сначала обсуждается с пользователем.

## Контракты

- `GET /health` возвращает `status` и `model_loaded`. Готовность к прогнозам определяется по `model_loaded`.
- `POST /predict` принимает `{"items":[{"shop_id":1,"item_id":2}]}`, возвращает `{"predictions":[{"shop_id":1,"item_id":2,"item_cnt_month":3.0}]}`. Сохраняй порядок и дубликаты. Коды ошибок — 400 для неизвестных ID, 422 для ошибок валидации, 503 при отсутствии предиктора.
- Сверяй HTTP-контракт с `src/pfs/api/` и `tests/api/`. При его изменении обновляй код, тесты и UML. Сохраняй возможность подставить `Predictor` через `create_app`.
- Для известной пары без истории сохраняй поведение холодного старта и ожидаемые моделью пропуски.
- Сохраняй имена, порядок, типы и кодирование признаков по `src/pfs/features/spec.py` и офлайн-расчёту. Используй историю строго до `target_month`.
- Сохраняй ограничение диапазона прогноза (`clip`). При изменении инференса сверяй признаки и прогнозы с офлайн-расчётом на фиксированном наборе пар.

## Среда и проверки

- Версия Python — в `.python-version`. Установка зависимостей из корня — `uv sync --locked`.
- Проверки — `uv run pytest`, `uv run ruff check .`, `uv run pyright`. Тесты по слоям — `uv run pytest tests/api` и `uv run pytest tests/features`.
- Тесты признаков требуют локальных скриптов из `tmp/scripts/`. Для теста на реальных данных задай `PFS_DATA_DIR` с путём к исходным CSV. README указывает `data/landing` для исходных данных.
- Храни данные и обученные артефакты вне Git. В репозитории держи код, конфигурацию и инструкции для их воспроизведения.


## Оформление
### Наименования

- Переменные и атрибуты — snake_case (`new_number`).
- Глобальные переменные и константы — UPPER_SNAKE_CASE (`NEW_NUMBER`).
- Функции и методы — snake_case (`get_number()`).
- Классы — PascalCase (`DataExtractor`).
- Имена должны быть осмысленными и на английском языке.

### Описание кода

- Каждый Python-модуль должен начинаться с краткого module docstring, описывающего его назначение и ответственность.
- Каждый класс должен содержать краткий docstring, описывающий его назначение.
- Каждая функция и метод должны содержать краткий docstring, объясняющий их назначение.
- При нетривиальной логике дополнительно описывай параметры, возвращаемые значения и возможные исключения.
- Docstring должны быть лаконичными, содержательными и не дублировать очевидную логику кода.
- Описание исключений на русском языке.
- Между функциями отступ 2 строки, между классами - 4.
